# Wave 0, Ticket 0.2 — Confirm Architecture

Wave: Repository Discovery and Technical Plan

Status: Complete

## Goal

Choose an implementation architecture that extends the application without replacing established patterns.

## Architecture Decisions

- Keep the application in Next.js and implement import, read, and export endpoints as App Router route handlers.
- Reuse Clerk authentication and scope every imported course query to the authenticated Clerk user ID.
- Reuse Supabase for persistence, adding versioned SQL migrations under `supabase/migrations`.
- Use separate imported-course tables so the catalog `courses` table retains its current semantics.
- Place the feature domain boundary under `lib/syllabus` for schemas, normalization, PDF parsing, LLM extraction, warnings, and persistence.
- Use Zod as the canonical runtime schema and inferred TypeScript contract.
- Parse only text-based PDFs and retain page boundaries. Reject image-only or low-text documents; OCR remains out of scope.
- Put LLM access behind a provider adapter and extraction service. Use structured output and validate again locally.
- Preserve page number and bounded source text for extracted assessments.
- Generate `.ics` files before OAuth integrations. Use recurrence rules for meetings and stable event UIDs.
- Use Vitest, fixture-based regression tests, strict TypeScript, ESLint, and production builds.

## Planned API Surface

- `POST /api/courses/import`
- `GET /api/courses/[courseId]`
- `GET /api/courses/[courseId]/calendar/classes.ics`
- `GET /api/courses/[courseId]/calendar/assessments.ics`
- Direct provider endpoints only after ICS export is stable.

## Definition of Done

- Reusable components and required new modules identified.
- Database, API, LLM, PDF, calendar, and testing strategies documented.
- Decisions preserve the strict structured-data boundary and conservative extraction rules.
